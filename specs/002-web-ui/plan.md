# Implementation Plan: Dodoo Web UI

**Branch**: `002-web-ui` | **Date**: 2026-06-06 | **Spec**: [spec.md](spec.md)

## Summary

Build a self-contained `web` addon (`dodoo/addons/web/`) that adds an Odoo-like browser UI on top of the existing dodoo JSON-RPC API. The UI is a single-page application (SPA) built with vanilla JS and served as static files from FastAPI. It provides five screens: login, home/app menu, list view, form view, and navigation (breadcrumb + sidebar). No new backend models or database tables are introduced.

## Technical Context

**Language/Version**: Python 3.12 (addon scaffolding) + Vanilla JS ES2022 (frontend, no build step)

**Primary Dependencies**:
- `starlette.staticfiles.StaticFiles` — already bundled with FastAPI; mounts the `static/` directory
- `playwright` (dev) — e2e browser testing

**Storage**: None — no new database tables. `sessionStorage` in the browser for session token.

**Testing**: pytest + playwright for e2e; existing pytest-asyncio for integration tests of the serving layer

**Target Platform**: Evergreen desktop browsers (Chrome, Firefox) on localhost

**Project Type**: Browser SPA served as a FastAPI static addon

**Performance Goals**: Initial load < 2s; client-side navigation < 300ms; list render (50 rows) < 500ms

**Constraints**: No external CDN calls; no JS bundler/transpiler; offline-capable after first load; no new Python backend dependencies beyond `playwright` (dev-only)

**Scale/Scope**: Single-tenant localhost; 5 screens; ~5 JS modules; ~1 CSS file

## Architecture

### Routing (Hash-Based)

All navigation uses `window.location.hash`. The router listens for `hashchange` and `load` events and delegates to view modules.

| Hash pattern | View module | Mode |
|---|---|---|
| `#/login` | `views/login.js` | — |
| `#/home` | `views/home.js` | — |
| `#/module/:name` | `views/home.js` | module detail |
| `#/model/:name` | `views/list.js` | list |
| `#/model/:name/new` | `views/form.js` | create |
| `#/model/:name/:id` | `views/form.js` | edit |

### Global State (app.js)

```js
App.state = {
  token: null,        // string | null — from sessionStorage on boot
  uid: null,          // integer | null
  modules: [],        // Module[]  — from /web/core/info
  models: [],         // string[]  — from /web/core/info
  fieldCache: {},     // { [modelName]: { [fieldName]: FieldMeta } }
}
```

### View Lifecycle

Each view file exports `{ render(container, params) }` and optionally `{ destroy() }`. The router clears the main container and calls `render()` on the incoming view.

### XSS Prevention

All API-returned strings inserted into the DOM MUST use `element.textContent` or `element.setAttribute()`. A shared `esc(str)` utility HTML-encodes any string before use in template literals that feed `innerHTML` on structural (non-data) content only.

### Session Expiry

`api.js` intercepts JSON-RPC error code `-32000` and navigates to `#/login?reason=expired`. The login view reads `reason` from the query string and shows a "Session expired" banner.

## Implementation Phases

### Phase 1 — Addon Scaffold + Static Serving
`__manifest__.py`, `__init__.py`, `http/__init__.py` (StaticFiles mount + `/web/client` route), minimal `index.html` and `style.css`. Integration test. 3 ADRs.

### Phase 2 — Core JS: api.js + app.js Router
`api.js`: `rpc()`, `authenticate()`, `logout()`, token injection, error handling.
`app.js`: hash router, `App.state`, layout shell (header + sidebar placeholder + main + breadcrumb).

### Phase 3 — Login Screen (US1)
`views/login.js`: form render, submit handler, success redirect, error display, session persistence, logout handler. Playwright e2e for US1.

### Phase 4 — Home Screen (US2)
`views/home.js`: fetch modules from `/web/core/info`, render tile grid with icons, click → navigate to list. Playwright e2e for US2.

### Phase 5 — List View (US3)
`views/list.js`: generic by model name; `fields_get`, `search_read`, table render, search filter, pagination, "New" button, row click. Playwright e2e for US3.

### Phase 6 — Form View (US4)
`views/form.js`: `read` record, render field controls by type (char→text, integer/float→number, boolean→checkbox, date→date, text→textarea, many2one→text+id), dirty tracking, Save/Discard/Delete, required validation. Playwright e2e for US4.

### Phase 7 — Navigation + Polish + CI (US5)
Breadcrumb wired to router state; sidebar model list; keyboard nav; `style.css` polish; axe-playwright a11y tests; CI e2e job in `ci.yml`; playwright added to `pyproject.toml [dev]`.

## Key Implementation Rules

1. **Never `innerHTML` with API data** — use `textContent` or DOM construction
2. **All fetch calls through `api.js`** — no inline `fetch()` in view files
3. **`fieldCache` populated once per model** — `fields_get` on first visit, reused thereafter
4. **Pagination offset** held in list view closure, not global state
5. **Discard** restores from `originalValues` snapshot — no round-trip to server
6. **Delete requires `window.confirm()`** before `unlink` call
7. **Readonly fields** rendered as `<span>`, not `<input>`
8. **Many2one** displayed as related record name; edited as integer ID input
